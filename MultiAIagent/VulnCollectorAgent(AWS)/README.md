# VulnCollectorAgent(AWS)

이 런타임은 취약점 원문을 그대로 넘기는 역할이 아니라, **동일한 CVE를 downstream 목적에 맞는 서로 다른 payload로 가공하는 역할**을 합니다.

현재 생성하는 결과는 4개입니다.

- `raw_dataset`
- `risk_assessment_payload`
- `operational_impact_payload`
- `asset_matching_payload`

핵심은 이 에이전트가 “취약점 하나를 여러 관점으로 다시 정리해 주는 입구”라는 점입니다.

## 현재 구조

현재 구조는 예전처럼 공통 normalizer 하나가 모든 결과를 만드는 방식이 아닙니다.  
지금은 목적이 다른 두 개의 agent가 각각 자기 기준으로 조사하고 정리합니다.

전체 흐름은 아래처럼 이해하면 됩니다.

```text
취약점 수집 런타임 시작
-> risk_assessment_payload 생성
-> operational_impact_payload 생성
-> asset_matching_payload 생성
-> raw_dataset 함께 반환
```

중요한 점:
- `risk`와 `operational`은 같은 raw 결과를 그대로 공유해서 쓰지 않습니다
- 각자 자기 목적에 맞게 다시 조사하고 정리합니다
- `asset_matching_payload`는 상대적으로 단순한 seed payload입니다
- `raw_dataset`은 현재 구조에서 공통 완성 데이터셋이라기보다, 경량 raw 결과에 가깝습니다

## 역할 분리

### 1. risk 쪽

이 경로는 **위험도 평가 에이전트가 읽기 좋은 취약점 기준 정보**를 만듭니다.

즉 이쪽이 하는 일은:
- 무엇이 영향을 받는가
- 어떤 조건에서 악용되는가
- 자산에서 무엇을 확인해야 하는가

를 정리하는 것입니다.

이 결과는 최종 위험도 판정이 아니라, **위험도 평가를 위한 참고 payload**입니다.

### 2. operational 쪽

이 경로는 **패치나 완화 조치를 실제 운영 환경에 적용할 때 필요한 정보**를 만듭니다.

즉 이쪽이 하는 일은:
- 우선해야 할 정식 조치가 무엇인가
- 패치 적용 시 무엇이 깨질 수 있는가
- 패치 전에 무엇을 확인해야 하는가
- 즉시 패치가 어렵다면 어떤 완화 조치를 고려할 수 있는가
- 적용 후 무엇을 검증해야 하는가

를 정리하는 것입니다.

이 payload는 보안 위험도 평가용이 아니라, **운영 영향도와 패치 전략 참고용**입니다.

### 3. asset matching 쪽

이 경로는 자산 매칭 단계에서 사용할 간단한 seed payload를 만듭니다.

즉:
- 어떤 제품을 찾아야 하는지
- 어떤 버전 범위를 봐야 하는지

정도의 최소 기준을 내려주는 역할입니다.

## 현재 조사 방식

현재 구조에서 `risk`와 `operational`은 각각 별도의 agent처럼 동작합니다.

둘 다 필요하면 스스로 조사 도구를 사용해 정보를 채웁니다.

조사 방향은 대체로 다음과 같습니다.

```text
CVE 확인
-> 필요하면 CWE 확인
-> 필요하면 NVD context, KEV, patch/reference 같은 공식 근거 확인
-> 자기 목적에 맞는 JSON payload 생성
```

즉 현재 구조는:
- 공통 초기 수집을 한 번만 하고 나눠 쓰는 구조가 아니라
- 각 agent가 자기 목적에 맞게 필요한 만큼 확인하고 채우는 구조입니다

## 결과물 설명

### `risk_assessment_payload`

이 결과는 위험도 평가 에이전트가 자산 정보와 결합해서 판단할 수 있도록 만드는 취약점 참고 자료입니다.

핵심 내용:
- 취약점 제목
- 영향 범위
- exploit 조건
- 자산에서 확인해야 할 체크리스트

특징:
- 설명형 필드는 한국어 중심으로 정리됩니다
- 상단에 field description 정보가 포함됩니다
- “최종 위험도 결과”가 아니라 “위험도 평가용 입력”입니다

### `operational_impact_payload`

이 결과는 패치 적용 시 운영 영향과 의존성 문제를 downstream 에이전트가 해석할 수 있게 만드는 자료입니다.

핵심 내용:
- 정식 조치
- 운영상 깨질 수 있는 부분
- 패치 전 확인 체크리스트
- 임시 완화 조치
- rollout guidance
- validation check

특징:
- 운영 영향도를 넓게 나열하는 방식이 아니라,
  **패치 전 확인 / 못 하면 완화 / 적용 후 검증** 중심으로 정리됩니다
- 상단에 field description 정보가 포함됩니다

### `asset_matching_payload`

이 결과는 자산 매칭 단계에 넘길 최소 seed payload입니다.

핵심 내용:
- CVE 기준 제품명
- 영향받는 버전 범위

### `raw_dataset`

이 결과는 현재 구조에서 예전처럼 모든 payload의 공통 기반이 되는 완성형 dataset은 아닙니다.

지금은:
- asset matching 쪽이 참고할 수 있는 raw seed 성격이 강하고
- risk 및 operational 쪽은 이를 그대로 재사용하기보다 각자 다시 조사합니다

## evidence_mode 개념

현재 런타임은 evidence 수집 강도를 조절하는 모드를 가집니다.

- `off`
  - 추가 evidence 없이 CVE/CWE 수준 정보만으로 정리합니다
- `auto`
  - 정보가 부족할 때 agent가 스스로 evidence를 더 볼지 결정합니다
- `on`
  - NVD context, KEV, patch/reference 같은 공식 근거 확인을 강하게 유도합니다

즉 evidence 수집은 항상 고정으로 일어나는 것이 아니라, 현재 모드와 agent 판단에 따라 달라집니다.

## runtime 동작 주의점

현재 runtime은 완전히 범용 입력형으로 열려 있는 구조는 아닙니다.

즉 현재 기준으로는:
- 외부에서 모델 ID나 일부 설정은 넘길 수 있지만
- 처리할 CVE 목록을 runtime payload에서 직접 자유롭게 바꾸는 구조는 아직 아닙니다
- 기본 CVE 목록 기준으로 동작하는 성격이 남아 있습니다

따라서 이 런타임은 지금 시점에서는
**범용 취약점 수집 API**라기보다  
**특정 CVE 세트를 기준으로 downstream payload를 생성하는 런타임**에 더 가깝습니다.

## 빌드 방식

이 런타임은 코드 ZIP 형태로 패키징되는 구조입니다.

즉 빌드 시에는:
- Python 의존성을 대상 플랫폼에 맞게 설치하고
- 런타임 진입 코드와 수집 로직을 함께 묶어서
- 최종 배포 ZIP을 생성합니다

현재 구조는 Strands agent를 실제로 사용하므로, 관련 의존성이 빠지면 payload 생성이 동작하지 않습니다.

## 현재 설계 요약

현재 구조는 이렇게 이해하면 됩니다.

```text
동일한 CVE를
1. 위험도 평가용 시각으로 한 번 정리하고
2. 운영 영향/패치 전략용 시각으로 다시 한 번 정리하고
3. 자산 매칭용 seed는 단순 구조로 별도 생성한다
```

즉 이 런타임의 핵심은:
- 취약점 원문을 단순 저장하는 것이 아니라
- **downstream 에이전트가 바로 쓸 수 있는 형태로 목적별 payload를 만들어 주는 것**

입니다.
